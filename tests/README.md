# `tests/` frontend verification map

These tests validate browser/client behavior. They intentionally mock/intercept Supabase calls, so they prove frontend integration contracts rather than live database/deployment health.

## Files

- `contracts.mjs` — fast deterministic client contract checks.
- `run-flow.cjs` — starts/stops the local Next.js server used by browser flows.
- `flow.cjs` — assessment, result, claim, cognitive-pilot and analytics flow.
- `funds-flow.cjs` — connected ETF research/Match/Screener/Compare/account flow.
- `m4-launch-flow.cjs` — M4 research/privacy/disclosure checks.
- `assets-flow.cjs` — cross-asset Explore/Detail/Compare behavior.
- `artifacts/` — ignored screenshots/output generated by browser regressions.

## Commands

```sh
npm test
npm run test:flow
npm run test:funds
npm run test:m4
npm run test:assets
npm run test:all
```

Browser suites use port 3001 by default and can use an installed Chrome via `CHROME_BIN`.

## Test-fixture rules

1. Fixtures should model the public API contract, not database internals that the browser should never see.
2. New browser RPC/Edge calls must be added to the relevant route interceptor; an `Unexpected request` failure usually means the frontend contract changed without the test fixture changing.
3. Do not hide real race conditions with arbitrary sleeps. Wait for route/state-specific markers.
4. Keep missing research data as `null` in fixtures when testing unavailable-data semantics.
5. Tests may mock auth/email callbacks; they must not be described as proof of real external email delivery.

## When to add a test

- assessment persistence/storage behavior -> `contracts.mjs` and/or `flow.cjs`;
- ETF-specific research/Match/account behavior -> `funds-flow.cjs`;
- cross-asset research behavior -> `assets-flow.cjs`;
- research/privacy/launch disclosure -> `m4-launch-flow.cjs`;
- RLS/RPC/data integrity -> add a SQL test in `supabase/tests/`, not only here.

See `docs/TESTING.md` for what each layer proves and does not prove.
